# 芝加哥餐饮选址顾问：产品设计思路（基于 BrewGap 微调）

文档状态：设计草案，2026-11-14。技术栈为 OpenAI API、Exa（用户写作 "EAX"，按比赛赞助方理解为 Exa 搜索）和 Base44。本阶段不接外部 API，先把数据、算法和报表结构定下来。

## 1. 一句话定位

给咨询师用的选址分析工具。咨询师输入客户的预算范围和餐厅类型，系统在芝加哥找出"同等预算下回报最高、竞争最少"的街区，并输出一份可追溯的报表，内容包括店面租金、人工成本、启动成本、月度损益、回本周期、推荐客单价、竞争压力和目标客群。

和 BrewGap 一脉相承的核心原则不变：所有数字由代码计算，大模型只负责编排工具和写解释；网页上的实时信息由 Exa 检索，每条都附来源链接。咨询师审核通过后，报表才交给客户。

相比 BrewGap，这一版有三处升级。第一，从单一业态（咖啡店）扩展到多菜系，每个菜系单独算需求缺口。第二，在"哪里缺店"之上加了一层财务模型，回答"开了能不能赚钱、多久回本"。第三，加入预算约束和优化：在预算之内，比较不同街区和不同店面规模的组合，挑出风险调整后收益最高的方案。

## 2. 用户与使用场景

主要用户是咨询师。他为每个客户建一个项目，录入需求，跑分析，检查和调整假设，然后把报表分享给客户。次要用户是餐饮经营者本人，只看只读的报表页面。

典型流程是：咨询师新建项目，填写预算和菜系；系统先给出候选街区的排名和财务测算；agent 再用 Exa 核实这些街区的实时挂牌租金、近期开关店和本地风险；咨询师调整假设（比如客户已经谈好了某处铺面的租金），系统重新计算；最后确认并导出报表。

## 3. 输入

| 字段 | 示例 | 用途 | 必填 |
|---|---|---|---|
| 预算范围（总启动资金） | 20 万到 35 万美元 | 限定可承受的面积、装修档次和租金水平 | 是 |
| 餐厅类型 | 意大利菜（含披萨店）、牛排馆、快餐、亚洲餐厅（作为一个整体分析） | 对应 Overture 的菜系分类，决定竞争对象和成本模板 | 是 |
| 服务形式 | 快餐、快休闲、正餐 | 决定人员配置、翻台模型、外卖占比 | 否，按菜系给默认值 |
| 面积偏好 | 1,500 到 3,000 平方英尺 | 生成候选面积档位 | 否 |
| 铺面类型 | 空置铺面、现成餐饮铺面（二手铺面） | 决定装修成本、转让费和可选铺面的范围 | 否，默认两种都考虑 |
| 是否需要酒牌 | 是 | 排除有酒牌限制的区域 | 否 |
| 营业时段 | 午餐、晚餐、夜宵 | 影响客流结构和人工排班 | 否 |
| 风险偏好 | 保守、平衡、进取 | 决定排序时看保守情景还是基准情景 | 否 |

没填的字段用菜系模板的默认值，并在报表的假设表里列出来，咨询师可以逐项修改。

**预算口径（已确认）：预算指总启动资金。** 它是一次性的投入上限，包括装修、设备、押金、牌照许可、开业前费用，以及开业后的营运资金储备。营运资金储备默认算在预算之内：一个方案即使装修和设备都付得起，如果剩下的钱撑不过开业爬坡期，也算不可行。月租不由用户直接输入，而是由系统推算：租金越高，押金越多，每月现金流越少，回本越慢。所以"能承受多高的租金"是模型算出来的结果，不是约束条件。

**铺面类型（已确认）：两种都考虑。** 空置铺面需要从头装修，包括排烟罩、隔油池、上下水和无障碍改造，前期投入高，但布局可以按自己的需求来。现成餐饮铺面（之前开过餐厅、厨房设施还在）装修省钱、开业快，但往往要付一笔转让费或设备买断费，设备状况不确定，而且前一家店为什么关门本身就是风险信号。两种类型的启动成本结构完全不同，所以作为优化时的一个独立维度，而不是一个开关。

**亚洲餐厅口径（已确认）：作为一个整体。** 范围按 Overture 的分类层级来定：asian_restaurant 之下的所有子类，包括东亚（中餐、日料和寿司、韩餐、台湾菜、蒙古菜）、东南亚（泰餐、越南菜、菲律宾菜、印尼菜、缅甸菜）、南亚（印度、巴基斯坦、尼泊尔、孟加拉菜）、中亚（阿富汗菜）以及拉面店。另外加上 Overture 归在国际融合菜下面的亚洲融合菜（asian_fusion_restaurant）和泛亚菜（pan_asian_restaurant）。南亚菜默认按 Overture 的层级算进来，如果咨询师认为印度菜等不属于客户的竞争范围，可以排除。

作为整体分析的好处是样本量大，模型更稳；代价有两个。第一，竞争压力可能被高估：一家泰餐和一家寿司店在模型里算作互相竞争，但它们抢的客人未必重叠，在菜系多样的街区这种高估更明显。所以位置卡上的竞争对手列表会保留每家店的子菜系标签，只作展示、不进模型，方便咨询师自己判断。第二，成本差异大：寿司店的食材成本率和面馆差很多，统一用一套成本模板，参数区间就要放宽，回本周期的区间也会相应变宽。

**意大利菜口径（已确认）：包含披萨店。** Overture 本身就把披萨店（pizza_restaurant）放在 italian_restaurant 层级之下，所以范围取 italian_restaurant 下的全部子类。另外加上 Overture 归在生活服务下的外送披萨（pizza_delivery_service）。

这个口径有一个明显的后果：在密歇根数据里，披萨店是传统意大利餐厅的约 6 倍（3,942 家对 625 家），其中约 40% 是连锁品牌（Little Caesars、Domino's、Pizza Hut 等）。芝加哥披萨文化浓厚，比例很可能也不低（接入芝加哥数据后核实）。所以意大利菜的需求模型主要反映的是披萨需求；客户如果想开的是坐下吃饭的意大利餐厅，"缺口"信号里有相当一部分来自披萨。应对办法是利用已有的服务形式维度：成本模板按"菜系 × 服务形式"来定，披萨店套快餐或快休闲模板（外卖占比高、客单价低、面积小），意大利正餐套正餐模板。竞争对手列表保留"披萨 / 意大利正餐"的子类型标签和是否连锁的标记，只作展示、不进模型。另外，由于全市披萨店密集，意大利菜的竞争压力分数整体会偏高，但街区之间的相对排名仍然有意义。

## 4. 输出报表结构

报表分五部分。

**第一部分：摘要。** 给出排名前三的方案，每个方案写明街区、业态、建议面积、推荐客单价、回本周期区间（保守、基准、乐观三种情景）和竞争压力等级。

**第二部分：每个推荐地点的详情卡。** 包括：

| 板块 | 内容 |
|---|---|
| 竞争压力 | 0 到 100 分，拆成同菜系密度、全部餐厅密度、近 12 个月新开店数、需求缺口四项 |
| 目标客群 | 由数据驱动的客群画像，比如"白天写字楼上班族为主，25 到 44 岁占比高，家庭收入在全市前 20%" |
| 租金 | 模型估算的每平方英尺年租金和月租总额，与 Exa 找到的实时挂牌价并列显示，差距大时标注 |
| 人工 | 按人员配置模板算出的月度人工成本，含小费岗位工资和雇主税费 |
| 启动成本拆分 | 装修、设备、押金、牌照许可、开业前费用、营运资金储备 |
| 月度损益 | 收入、食材成本、人工、租金、其他运营费用、净现金流 |
| 回本周期 | 三种情景下累计现金流转正的月数，含开业爬坡期 |
| 铺面类型对比 | 同一地点并排给出"空置铺面"和"接手现成餐饮铺面"两套方案，比较启动成本、回本周期和风险；只有该区域有二手餐饮铺面的证据时才给第二套 |
| 敏感性分析 | 客单价、客流、租金、食材成本各变动 ±10% 时回本周期怎么变（龙卷风图） |
| 风险 | 该区域同类店的历史关店率、酒牌限制、施工或开发项目、近期新开的竞争者 |
| 证据 | Exa 检索到的网页，附标题、日期和链接 |

**第三部分：同预算对比。** 第一张图是候选方案的"回本周期 vs 风险"散点图，让客户一眼看出哪些方案又快又稳。第二张图是"街区 × 菜系"的需求缺口矩阵：如果客户对菜系不执着，可以看到同样的预算换个业态会不会更好。

**第四部分：假设表。** 列出每个参数的取值、来源、日期，以及是否被咨询师改过。

**第五部分：方法与局限。** 用通俗的话说明模型怎么算、验证结果如何、哪些东西模型看不到。

关于公平性：客群匹配只用收入、年龄、家庭结构、上班族、学生、酒店游客、交通客流这类消费相关的特征，不用种族或族裔，避免把"什么人吃什么菜"的刻板印象写进模型。

分析单位：芝加哥市区密度高，建议用 H3 分辨率 9（约 0.1 平方公里，相当于两三个街区），竞争和需求按周围 1 到 2 圈汇总，报表摘要再汇总到 community area。BrewGap 用的是分辨率 8，因为密歇根的城镇更稀疏。

## 6. 计算核心（全部是确定性代码）

### 6.1 各菜系的需求缺口

沿用 BrewGap 的做法，每个菜系训练一个 Poisson 模型，只用需求侧特征，预测每个格子"应该"有几家这类餐厅，再减去实际数量。芝加哥只有一个县，不能"留一县验证"，改成按芝加哥传统的 9 个"sides"（Far North、Northwest、North、West、Central、South、Southwest、Far Southwest、Far Southeast）轮流留出一个来验证。每个菜系都要和"数商家数量"这个笨基线做对比，并把结果写进报表的方法部分。以后可以再加入密尔沃基、明尼阿波利斯等城市的数据，提高模型的迁移能力。

### 6.2 竞争压力指数

由四项组成：周边同菜系实际店数与模型预期店数之比（大于 1 说明饱和）、周边全部餐厅密度、近 12 个月同菜系新开店数（来自 Food Inspections 的首次检查记录）、需求缺口。四项按距离加权，归一化到 0 到 100 分。报表里把四项分开列出，客户能看到分数是怎么来的。

### 6.3 目标客群匹配

模型对每个菜系都有一组需求驱动因素（BrewGap 里的 drivers，即相对"典型商业街区"的倍数）。拿候选街区的特征和该菜系的驱动因素对比，就能得到匹配度和客群画像标签。标签由规则从数据生成，比如"上班族占比位于全市前 10%"；大模型只负责把这些标签写成通顺的句子。

### 6.4 推荐客单价

三个输入：该菜系和服务形式的基准客单价区间（来自行业基准，必须有来源）、街区消费力指数（收入百分位，以及白天就业人口的收入结构）、周边竞品的价格定位（agent 用 Exa 找三到五家竞品的菜单价格，作为证据）。输出一个推荐区间，并说明相对周边竞品是偏低、持平还是偏高。价格弹性没有可靠数据，所以只在敏感性分析里展示客单价变动对回本周期的影响，不假装能算出"最优价格"。

### 6.5 财务模型

```
启动成本(空置铺面) = 全套装修(每平方英尺单价 × 面积，含排烟罩、隔油池、上下水、无障碍改造)
                  + 全套设备 + 押金(月租 × N 个月) + 牌照许可 + 开业前费用
                  + 营运资金储备(覆盖 M 个月的固定成本)

启动成本(现成餐饮铺面) = 翻新装修(单价远低于全套装修) + 转让费或设备买断费(来自挂牌信息)
                      + 设备检修与补齐 + 押金 + 牌照许可 + 开业前费用 + 营运资金储备
                      开业准备期更短，所以爬坡前的空租月数更少

两种类型各自的参数(装修单价、设备检修比例、准备期月数)都要有可引用的来源

月收入   = 日客数 × 客单价 × 营业天数 × 爬坡系数(开业头几个月低于 100%)
日客数   = min(产能上限, 需求可承接量)
           产能上限：正餐用 座位数 × 翻台率 × 上座率；快餐用 高峰时段出餐能力
           需求可承接量：该菜系单店年营收基准 ÷ 客单价，再乘以需求调整系数
             (周边预期店数 / 实际店数，设上下限，避免缺口过大时收入被无限放大)

月成本   = 食材(收入 × 菜系食材成本率) + 人工(人员配置模板 × 工时 × 芝加哥工资标准 × (1 + 雇主税费率))
         + 租金(基础租金 + NNN 分摊的物业税、保险、公共维护费) + 水电燃气 + 保险 + 营销
         + 刷卡手续费 + 外卖平台佣金(按外卖占比) + 维修

回本周期 = 累计净现金流首次超过启动成本的月份
```

情景分析：每个参数都给一个区间，而不是一个固定值。用蒙特卡洛模拟（约 1000 次抽样）得到回本周期的 P10、P50、P90，对应报表里的乐观、基准、保守三种情景。

### 6.6 预算内优化

对每个候选格子，按三档面积（小、中、大）、适用的服务形式和两种铺面类型组合出方案。"接手现成餐饮铺面"的方案只在有证据时生成：要么 Exa 找到了该区域的二手餐饮铺面挂牌，要么 Food Inspections 显示附近最近有餐厅关门、铺面可能空出。有挂牌时用挂牌的租金、面积和转让费；只有关店记录时，按区域估算值计算，并在报表里注明"铺面是否在租未确认"。如果同一地址历史上多次关店，方案标上"同址多次关店"的风险。启动成本本身也有不确定性（装修超支很常见），所以它同样用区间来模拟。可行性的判断规则如下：基准情景（P50）的启动成本含营运资金储备，不超过预算上限的方案才保留；如果保守情景（P90）的启动成本超过了预算上限，就给方案标上"超支风险"；如果连基准情景的启动成本都低于预算下限，就标上"预算有余"，提示客户可以把省下的钱留作额外储备，或者考虑更大的面积。剩下的方案按风险偏好排序：保守型看 P90 回本周期，平衡型看 P50，进取型看 P50 年利润。同一个街区只保留最优的一种面积，然后输出前三名和完整的散点图。这一步就是"同等预算下获得更大收益"的实现方式。

## 7. Agent 设计（OpenAI + Exa）

Agent 的职责是编排、核验和解释，不做计算。

| 工具 | 输入 | 输出 | 是否确定性 |
|---|---|---|---|
| screen_areas | 菜系、预算、服务形式、风险偏好 | 优化器筛出的前 N 个方案 | 是 |
| get_area_profile | 格子或社区编号 | 需求驱动因素、客群标签、竞争压力四项、关店率、近期关门餐厅的地址、同址历史关店次数 | 是 |
| estimate_financials | 格子、菜系、面积、铺面类型、客单价、租金和转让费的覆盖值（可选） | 启动成本、月度损益、三种情景的回本周期、敏感性结果 | 是 |
| search_listings | 街区、面积区间、铺面类型 | 挂牌租金、面积、地址、是否为二手餐饮铺面、转让费、日期、链接 | 否，Exa 检索 |
| search_competitors | 街区、菜系 | 近期开关店、菜单价格样本、链接 | 否，Exa 检索 |
| search_local_risks | 街区 | 施工、开发项目、酒牌限制、规划变化、链接 | 否，Exa 检索 |

工作流程分六步。第一步，把输入整理成结构化需求，关键信息缺失（比如是否卖酒）时先问咨询师。第二步，调用 screen_areas 拿到候选方案。第三步，对前三名调用 get_area_profile 和 estimate_financials。第四步，用三个 search 工具做实时核验；Exa SDK 支持 output_schema 参数，可以直接从挂牌页面抽取"租金、面积、地址"这样的结构化字段。第五步，如果挂牌租金和模型估算相差超过设定阈值，用挂牌租金重新调用 estimate_financials，报表里两个结果都展示。第六步，按固定的 JSON 结构输出报表，由 Base44 渲染。

硬规则沿用 BrewGap：报表里的数字只能来自工具结果；网页上的说法必须附链接；数据不足时要明说；报表默认是草稿状态，咨询师审核后才能分享给客户。

## 8. Base44 架构

```
离线（Python，复用 BrewGap 管线）              Base44（线上）
──────────────────────────────                ─────────────────────────────────────────
ACS / LODES / Overture / Food Inspections      实体（数据库）
/ Assessor 估值数据                             Area、CuisineGap、RentEstimate、Benchmark
   → build_features.py（改为伊利诺伊）            Client、Project、Scenario、Report、Evidence
   → train.py（每个菜系一个模型，按 side 验证）     ↑ 导入离线产出的表
   → 导出 CSV/JSON ───────────────────────────▶
                                               后端函数（Deno TypeScript，密钥放在 Secrets）
                                               computeFinancials：财务模型和优化器，确定性
                                               runAgent：OpenAI 工具调用循环
                                               exaSearch：Exa 检索和结构化抽取
                                               页面
                                               项目列表 / 新建分析 / 分析进度（agent 时间线）
                                               报表页 / 客户只读分享页 / 假设库管理
```

分工上，Base44 负责界面、登录、数据库、托管和后端函数。根据 Base44 官方介绍，后端函数是运行在 Deno 上的 TypeScript，可以读取 Secrets、调用外部 API，所以 OpenAI 和 Exa 的 key 放在服务端，不暴露给浏览器。数据准备和模型训练比较重，放在离线的 Python 管线里完成：直接复用 BrewGap 的 `build_features.py` 和 `train.py`，改成伊利诺伊的数据源，再加上按菜系训练和按 side 验证。产出的表导入 Base44。数据量很小：芝加哥市区在分辨率 9 下大约几千个格子，乘以四到八个菜系，Base44 的实体完全放得下。

财务模型写成 Base44 后端函数里的纯函数，同样的输入一定得到同样的输出，方便单元测试，咨询师改了假设也能立刻重算。

有两点要在动手的第一个小时验证：Base44 生成的前端能不能引入地图库（Leaflet、MapLibre 之类）；Base44 项目能不能导出到 GitHub，以满足比赛"公开 GitHub 仓库"的要求。

## 9. 分阶段

**没有历史数据时的做法（已确认目前没有）：** 收入和人工的基准改用公开的本地统计（第 5 节的 Economic Census、County Business Patterns、QCEW），报表里所有收入和回本数字都标注"未经本地经营数据校准"。同时建议在 Base44 里预留一个 Outcome 实体：客户签约或开业后，咨询师记录实际租金、实际装修花费和开业后的月营收。这样每做一个项目，校准数据就多一条，第三阶段才有数据可用。这个实体只是建议，要不要做由你决定。

| 阶段 | 内容 | 是否需要外部 API |
|---|---|---|
| 第一阶段 | 离线跑出芝加哥各菜系的缺口、竞争压力、客群和租金估算；Base44 搭建页面、实体和 computeFinancials；报表文字先用模板生成 | 否 |
| 第二阶段 | 接入 OpenAI agent 和 Exa 实时核验，报表文字改由 agent 生成，并附证据 | 是 |
| 第三阶段 | 用真实的客户经营数据校准收入和成本参数，这也是竞争对手很难复制的壁垒。咨询公司目前没有历史项目数据（已确认），所以这一阶段要等数据积累起来再做 | 否 |

## 10. 和比赛要求的对应

Future of Intelligence 赛道要求基于 OpenAI 和 Exa 做出"必须有 agent 才能存在"的东西。这个产品满足：实时挂牌租金和近期开关店信息只能从网上查，而选址排名和回本测算来自确定性模型，不是一层薄包装。Best Use of Base44 赛道要求用 Base44 做出一个可访问的线上链接，由社区投票评选；这个应用本身就是在 Base44 上搭建和托管的。两个赛道可以同时报。

时间是最大的风险。现在是周六下午，周日中午 12 点截止，而这一版要把地区从密歇根换到芝加哥，还要新增多菜系模型、财务模型和整个 Base44 应用。如果时间不够，按这个顺序砍：先把蒙特卡洛换成三组固定情景，再去掉跨菜系矩阵，最后把分析单位从 H3 格子退到 77 个社区。

## 11. 局限（要写进报表）

收入估算是整个模型最弱的一环：没有真实的 POS 数据，咨询公司目前也没有历史项目数据，只能用"公开统计的单店营收基准 × 需求调整系数"来推算，所以只给区间，不给一个确定的数，并标注"未经本地经营数据校准"。Economic Census 的单店营收是全部同类餐厅的平均，不分菜系，也不区分新店和老店，新店头几年的营收通常低于平均水平，这一点要靠爬坡系数来近似。需求模型验证的是"预测哪里有这类餐厅"的能力，不等于预测哪家店赚钱。租金估算依赖估值数据的覆盖面和挂牌信息的时效。Overture 的菜系标签有噪声。接手现成餐饮铺面时，设备和管线的实际状况只能靠实地查看，转让费也要谈判，模型里用的是区间；酒牌和营业执照不能默认随铺面转给新经营者（芝加哥的具体规定待核实），要按新店重新申请，审批时间计入开业准备期。回本周期是按假设推算的情景，不是承诺；报表要附免责声明，并由咨询师审核后再交给客户。

## 12. 待确认的问题

已确认：预算指总启动资金（见第 3 节）；空置铺面和现成餐饮铺面两种都考虑（见第 3、6.5、6.6 节）；亚洲餐厅作为一个整体分析，范围按 Overture 分类层级定，南亚菜默认包含（见第 3 节）；意大利菜包含披萨店和外送披萨（见第 3 节）；咨询公司目前没有历史项目数据，收入和人工基准改用公开的本地统计（见第 5、9 节）。

业务口径的问题都已确认。剩下的是动手前要核实的数据细节：Assessor 估值数据里有没有每平方英尺租金字段；Economic Census 和 County Business Patterns 在芝加哥的具体表格和地理层级；CTA 客流数据；酒牌限制区的数据源；芝加哥酒牌和营业执照能否随铺面转让；Base44 前端能不能引入地图库、项目能不能导出到 GitHub。还有一项设计建议需要你拍板：要不要预留 Outcome 实体，用来积累校准数据（见第 9 节）。
